# ⚖️ Design Decisions & Tradeoffs

A baby tracker looked like simple CRUD when I started. Once I began modeling the data, I found plenty of real decisions hiding underneath, and each one had a tradeoff.

This document records what I chose, what I considered instead, and where my current design falls short. Some of these decisions will probably change as I learn more, and that's part of the point.

**Stack:** Angular · Angular Material · ASP.NET Core (.NET 10) · Entity Framework Core · PostgreSQL

> Each section separates what's **built today** from what's **planned**, so nothing here claims more than the code does.

---

## 🗂️ 1. Data Model

### One table per log type

Each log type (feeding, sleep, diaper, pumping) has its own table, rather than one shared `events` table with a `type` column. In EF Core terms, this is **Table-per-Concrete-type (TPC)** rather than **Table-per-Hierarchy (TPH)**.

| | One table per type ✅ | One shared `events` table |
|---|---|---|
| **Required fields** | Plain `NOT NULL` per type | Can't require a column for only some types without CHECK constraints keyed on `type` |
| **Readability** | Each table describes one thing | Many columns, mostly `NULL` on any given row |
| **CRUD** | Simple endpoints and DTOs per type | One generic endpoint that branches on type |
| **Adding a new log type** | New table, migration, and endpoints | No new table needed |

The cost is more boilerplate up front. I accepted that because each log type has genuinely different fields: a bottle feed needs an amount, a diaper change needs a type, and a pumping session needs left and right amounts. Once parents can create, edit, and delete each type from the frontend, simple per-type CRUD pays for itself.

### Shared code in C#, separate tables in Postgres

Separate tables don't mean duplicated code. The C# models use abstract base classes for what every log shares:

```text
BaseModel   Id, CreatedAt, UpdatedAt
└─ BaseLog   StartTime, Timezone, Notes
   ├─ BabyLog   BabyId
   │  ├─ FeedLog
   │  ├─ SleepLog
   │  └─ DiaperLog
   └─ PumpLog   UserId
```

The base classes aren't mapped to tables of their own, so each concrete log type gets its own table with the shared columns included.

### Pump logs belong to the parent, not the baby

Feeding, sleep, and diaper logs reference a baby. Pump logs reference the **user**, because pumping is the parent's activity, not the baby's. Attaching pump logs to a baby would mean picking a baby arbitrarily for families with more than one, and deleting a baby shouldn't erase a parent's pumping history.

### Why not one table with a JSONB column?

A common middle ground is a shared table with common columns, plus a `jsonb` column for type-specific fields. It's flexible, because a new log type doesn't need a migration.

I chose separate tables because I want mistakes caught as early as possible. I once forgot a field in a DTO, and that's exactly the kind of bug I want caught while I'm building, not when a parent is trying to log a feed at 3 a.m.

- **At compile time:** typed entities and DTOs catch a missing field before the code runs.
- **At the database:** even when JSONB is mapped to a typed C# class, Postgres doesn't enforce the JSON's shape. Anything that writes to the database outside the application (a script, a manual fix, a future service) could save invalid data. Separate tables enforce it with a plain `NOT NULL`.

If parents could ever define their own custom log types, JSONB's flexibility would be worth revisiting.

### GUID primary keys

The Today page shows every log type in a single timeline. With auto-incrementing integers, each table counts from 1, so "Feed #5" and "Diaper #5" would share an ID, and a combined list couldn't identify an item by its ID alone. GUIDs are unique across every table.

IDs are currently generated by Postgres with `gen_random_uuid()`, which produces random (v4) GUIDs.

| Pros | Cons |
|---|---|
| Unique across tables, so the timeline merges safely | Larger than integers (16 bytes vs. 4–8) |
| Could be generated client-side later, which would open the door to offline logging | Random (v4) GUIDs can fragment indexes as tables grow; time-ordered UUIDv7 is a possible future switch |
| Not guessable in URLs (an extra layer, not a replacement for authorization) | Harder to read while debugging |

### How the timeline is assembled

The timeline endpoint runs one query per log type for the requested date range, then merges the results in C# and sorts them by start time. Day boundaries are calculated in the parent's time zone, so "today" means the parent's today, not UTC's.

Merging in C# keeps each query simple and typed. At this app's size (a few dozen logs per day), the cost of four small queries is negligible. A SQL `UNION ALL` or a database view would be the next step if the timeline ever needed server-side pagination.

### Timestamps: UTC plus a stored time zone

Every log stores two things:

- **The moment it happened**, as a UTC timestamp, so times are unambiguous across time zones and daylight saving changes
- **The time zone it was logged in** (an IANA zone such as `America/Chicago`)

UTC alone records *when* something happened but not what the clock said where it happened. Without the stored time zone, a 3 a.m. feed logged in Chicago would show a different hour if viewed later from London. Storing both means the history reads the way the parent lived it, which matters for parents who travel with a baby.

### Text + CHECK constraints instead of Postgres enums

Columns with a fixed set of values, such as feed type, sleep location, and diaper type, use `text` with a `CHECK` constraint rather than a native Postgres enum. Multi-select fields like wake reasons and rash locations are `text[]` arrays checked with `<@` (every selected value must be in the allowed list).

I expect the allowed values to change as I learn what parents actually need, and changing a constraint is much easier than removing or renaming an enum value. Text columns also map to EF Core without extra enum configuration.

### Amounts in ounces

Feeding and pumping amounts are stored in ounces as `decimal(3,1)`: up to 99.9 oz with one decimal place. That's plenty for a single feed or pumping session, and a fixed decimal avoids the rounding surprises of floating-point numbers.

## ♻️ 2. Data Lifecycle: Soft Delete, Restore, and Purge

One of the principles in the README is **forgiving editing workflows**. The people using this app are tired, distracted, and often using one hand, so accidental deletes are a certainty, not an edge case.

### Built today

- **Babies are soft-deleted.** Deleting a baby sets a `DeletedAt` timestamp instead of removing the row, and every endpoint filters out deleted babies and their logs.
- **Logs are hard-deleted on purpose.** The goal is to protect what's expensive to lose, a baby's whole history, not what's cheap to recreate, like a single feed. It also avoids a common soft-delete bug, where restoring a baby would bring back logs the parent had deliberately deleted earlier.
- **A `DeletedAt` timestamp instead of an `IsDeleted` flag.** It records *when* something was deleted, which a future purge needs.
- **The database cascades deletes.** `ON DELETE CASCADE` runs from users to babies, from babies to their logs, and from users to pump logs. When a row is permanently deleted, everything that depends on it goes with it in one atomic statement, even if application code has a bug.

### Planned

| Entity | On delete | Restorable? |
|---|---|---|
| **User** | `DeletedAt` set; their babies are soft-deleted only if no other active parent remains | Within 30 days |
| **Baby** | `DeletedAt` set (built) | Within 30 days |
| **Log** | Hard-deleted immediately (built) | No |

- **User soft delete and restore endpoints**, for both accounts and babies, with a 30-day window
- **Re-registering with a soft-deleted email** points the user to restore their existing account instead
- **A deliberate decision on login for soft-deleted users:** today a soft-deleted user can still log in, which may become the restore path

### The purge job (planned)

After the 30-day window, a scheduled job will permanently delete expired rows, most likely an AWS Lambda triggered daily.

- **Idempotent:** each run deletes whatever is past the window. If a run fails partway through, the next one simply finishes the job.
- **Per-user atomicity:** each `DELETE` cascades through the database in one statement, so no user is ever left half-purged.
- **Batching:** deleting in fixed-size batches keeps each transaction short, instead of holding locks during one large delete.

Soft deletes cascade in application code, while the purge relies on database cascades. A soft delete is an `UPDATE`, and database cascades only fire on `DELETE`.

## 🛡️ 3. Validation by Layer

The README asks where validation and business rules should live. My answer so far is that each layer validates what it's best suited for:

| Layer | Responsibility | Status |
|---|---|---|
| **Frontend (Angular)** | Immediate feedback for the user; never trusted on its own | Planned |
| **API** | Business rules: required fields, password length, email format | Partly built: required fields and password length are checked; email format is planned |
| **Database** | Structural guarantees: required fields, unique email, allowed values via CHECK constraints | Built |

Email format validation belongs in the API rather than the database. Real-world email rules are messy, they're easier to test and change in C#, and the API can return a clear error attached to the right field. A valid format still doesn't prove an address is real; that takes a confirmation email.

The database's unique index on email is the real guarantee against duplicate accounts. An API check alone can't prevent two signups that arrive at the same moment, but the database constraint can.

## 🚧 Known Limitations & Next Steps

- **The Angular app currently runs against `json-server`, not the real API.** Connecting the two is the next major milestone.
- **Duplicate email signups return a 500.** The unique index correctly rejects them, but the API doesn't catch the error yet. It should return a `409 Conflict` with a clear message, and point soft-deleted users to restore.
- **Emails aren't normalized.** `Connor@example.com` and `connor@example.com` are currently treated as different accounts. The fix is lowercasing in the API, enforced by the database.
- **No frontend form validation yet.**
- **Soft-delete filtering lives in individual endpoints**, so a new endpoint could forget it. The next step is EF Core global query filters (`HasQueryFilter`), so deleted rows are excluded by default.
- **User soft delete, restore, and the purge job aren't built yet** (see the lifecycle section).
- **Deleted logs can't be recovered.** That's intentional, but a confirmation step or an undo toast would make it fit the "forgiving editing" principle better.
- **One parent per baby.** Babies reference users through a direct `user_id` foreign key. Supporting co-parents means moving to a `user_babies` join table with a `role` column. At that point, deleting a user removes their access instead of the baby.
